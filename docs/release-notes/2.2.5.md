# v2.2.5

The domain-fronting fallback (`--fronting-domain`) now also triggers when the
WebSocket handshake is killed outright — typically a TCP reset right after the
TLS ClientHello — instead of only when it runs out its timeout. On such
networks the proxy used to re-send the real `kws{N}.web.telegram.org` SNI on
every connection and never front at all, while logging that fronting was
enabled.

## Why

Fronting was gated on the handshake *timeout* alone. A DPI box that drops
packets produces exactly that timeout, but one that resets the connection
after reading the ClientHello surfaces as a transport error, which the gate
did not recognize. Both are the same signal: the ClientHello — the only thing
carrying the SNI — went out, and the connection died around it.

Pre-TCP-connect failures (connection refused, DNS errors, an outbound proxy
rejecting the CONNECT) are now classified separately and still do *not*
trigger fronting: nothing was established to talk TLS over, so a different
SNI changes nothing. An HTTP answer (non-101, non-redirect status) also keeps
the old treatment — TLS completed, so the SNI already got through.

## Scope

Direct WebSocket connections to a configured `--dc-ip` only, as before. The
Cloudflare proxy, Cloudflare Worker and upstream MTProto paths never front:
Cloudflare routes by SNI, and a fronted SNI would fail at their edge.

## Cost

On a network where the DC answers HTTP for its own reasons, a doomed fronted
retry now costs one extra `--ws-connect-timeout` before the fallback chain
moves on. The per-DC `--fronting-fail-cooldown` (default 60 s) bounds how
often that retry happens.
